# ADR-013: Golden AI eval set — shrink the trusted claim to the reviewed 30

- **Status**: accepted
- **Date**: 2026-09-16
- **Ticket**: Spike 2 (`docs/plans/gemini-hetzner-telugu-plan.md` Phase −1)

## Context

`docs/SPEC.md` §18 requires "≥300 representative stories" in the golden AI
eval set. `apps/api/eval/golden_set.json` has exactly 300 items and passes
that count today, but per its own `_meta.provenance` (and
`PROGRESS.md`'s 2026-09-09/2026-09-16 entries) only 30 are hand-written and
human-reviewed; the other 270 were bulk-generated by Claude on 2026-09-09,
verified only against the deterministic `qa.py`/`glossary.py` checks the
harness itself runs — never checked by a native Telugu speaker or
editorial staff for translation naturalness, register, or whether the
underlying English news copy is even realistic. `eval/README.md` already
flags this in its own words: "a real regression suite... for the parts of
this pipeline that aren't a live model call" — true of all 300, but the
270's *content* (not just its mechanical pass/fail behavior) is unverified
fiction.

Spike 2 (`gemini-hetzner-telugu-plan.md`, Phase −1) frames this as a binary:
"Either validate a real subset or shrink to the 30 human-reviewed items and
stop claiming §18's ≥300. A small honest set beats a large fictional one."

Validating a subset needs the same resource this session doesn't have for
Spike 1: a native Telugu speaker to grade translations for naturalness and
accuracy. That's a human-scheduling dependency, not something resolvable by
reading code or running scripts — so it can't be done in this session.
Shrinking is mechanically available now, but doing so directly contradicts
`docs/SPEC.md` §18's explicit "≥300" text, and per `CLAUDE.md`'s workflow
("if something is ambiguous or requires a legal/architecture assumption,
stop and write an ADR instead of guessing"), a change that puts the eval
corpus in conflict with the spec's own stated count is not something to
edit silently — it needs to be recorded as a decision and the spec amended
in the same breath if accepted, same pattern as ADR-013 (Telugu-first,
in the larger plan) is required to amend `NON_NEGOTIABLES.md` #7 alongside
itself.

## Decision

Recorded here as **proposed**, not yet implemented:

1. Amend `docs/SPEC.md` §18 from "≥300 representative stories" to "≥30
   human-reviewed representative stories, expanded only with items that
   have passed the same human review" — the count target moves from raw
   volume to reviewed volume.
2. `apps/api/eval/golden_set.json` shrinks to the 30 items listed in
   `_meta.human_reviewed_ids` (3 per category × 10 categories). The 270
   generated items are removed from the file, not merely unmarked — an
   unreviewed item sitting in a file that claims to be a "golden" set is
   the exact problem being fixed, whether or not code currently reads its
   provenance field.
3. `eval/README.md`'s "Corpus size" section is rewritten to describe a
   single-tier, 30-item, fully human-reviewed set — the two-tier
   provenance language is deleted along with the items it was disclosing.
4. Growing the set back past 30 requires the same bar every time: each new
   item is native-Telugu-speaker reviewed *before* it's committed, not
   bulk-generated and reviewed later. This ADR does not propose a
   mechanism for that review (no tooling/process exists yet) — just the
   rule that unreviewed items don't count toward the total.

Not implemented yet because accepting this ADR means SPEC.md itself
changes, which is a product-owner call (same reasoning as why ADR-006 and
ADR-011 sit proposed rather than silently enacted) — not something to
land in the same session that discovers the gap.

## Consequences

- Makes: the eval set's count claim honest — 30 real items a native
  speaker actually checked, instead of 300 where 90% are unverified.
  Removes the operational risk of someone trusting a "regression caught"
  result against fabricated news copy.
- Costs: §18's own stated threshold text has to change, which needs
  product-owner sign-off, not just an engineering fix; the set is smaller,
  so it's a thinner regression net per category (3 items) until real
  review capacity exists to grow it back with reviewed items.
- Revisit when: a native Telugu speaker is available to review a batch —
  at that point new items can be added past 30, `human_reviewed_ids` grows,
  and this ADR's #4 becomes a real reviewed-addition process rather than a
  bare rule.

## Alternatives considered

- **Validate the 270 in place** (Spike 2's other named option): rejected
  for *this session* only because no native Telugu speaker is available —
  not rejected on the merits. If review capacity shows up before this ADR
  is acted on, that path is strictly better (keeps the larger corpus) and
  should be preferred over shrinking.
- **Leave it at 300 and just fix the docs to disclose the split** (i.e.,
  keep today's state): rejected — `eval/README.md` already discloses the
  split today and the corpus still gets described elsewhere (`PROGRESS.md`,
  §18) as satisfying "≥300", which is the exact honesty gap Spike 2 was
  written to close. Disclosure without a count change doesn't fix the
  false "≥300 representative" claim SPEC makes.

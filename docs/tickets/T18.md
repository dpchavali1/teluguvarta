# T18 — Observability

**Depends on**: T08 through T17 (this ticket instruments the whole pipeline
built so far).

## Goal

Make failure and cost visible before hardening, not after.

## Scope

- Error tracking (Sentry or equivalent) wired into `apps/api`, `apps/web`,
  `apps/mobile`, `apps/admin`.
- Structured logs across API and workers — consistent fields (request_id,
  actor, job type, story_id where relevant) so incidents are traceable.
- Job health dashboard in admin (§9.3 "ingestion health", §14): per-source
  fetch success/failure, circuit-breaker state, job queue depth/age.
- AI cost dashboard in admin surfacing the telemetry from T10: tokens/cost
  by task/provider/source/story/day, and remaining budget against
  `MONTHLY_AI_BUDGET_USD`/`DAILY_AI_ALERT_USD`.
- Alerting: at minimum, an alert path (email/webhook — pick the simplest
  that works, no new infra) when a budget threshold, error rate, or job
  circuit-breaker trips.
- Core analytics events from §17 (`app_open, feed_view, story_open,
  story_save, story_share, language_switch, search, notification_open,
  notification_opt_in, onboarding_complete, account_delete_request,
  report_issue`) instrumented via the analytics provider chosen in §10.1
  (PostHog or equivalent).

## Acceptance criteria

- A deliberately thrown error in each app surfaces in the error tracker with
  useful context (not just a stack trace with no request/actor info).
- Admin can see, for the last 24h: per-source ingestion health, job queue
  state, and AI spend vs. budget.
- Crossing a configured budget/error threshold produces an observable alert
  in tests (even if delivered to a test channel).
- Every event in §17's core list fires at least once in an E2E smoke test.

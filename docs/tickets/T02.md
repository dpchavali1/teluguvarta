# T02 — Env + local setup

**Depends on**: T01.

## Goal

Any engineer (or agent) can clone the repo and get a working local
environment in one documented pass.

## Scope

- `.env.example` at repo root (and per-app if needed) listing every env var
  referenced anywhere in the spec: DB connection string, AI provider keys
  (names only, no real secrets), `MONTHLY_AI_BUDGET_USD`,
  `MONTHLY_INFRA_BUDGET_USD`, `DAILY_AI_ALERT_USD`,
  `AUTO_PUBLISH_DISABLE_ON_BUDGET_BREACH`, `AUTO_PUBLISH_GLOBAL`,
  `AUTO_PUBLISH_CATEGORY_IMMIGRATION`, `AI_TRANSLATION_ENABLED`,
  `PUSH_NOTIFICATIONS_ENABLED`, push/FCM/APNs credentials, object storage
  credentials. Never commit real values.
- Local Postgres: docker-compose (or equivalent) service definition for
  local Postgres with the extensions V1 needs (`pg_trgm` at minimum).
- Migration runner: pick a tool (e.g. Alembic for the FastAPI side) and wire
  it into `infra/migrations/`. No schema yet (that's T03) — just the runner
  and its config.
- Seed scripts under `infra/scripts/` — placeholder that will later seed
  topics, a few sources, and test users (filled in as T03/T06 land).
- README: local setup instructions (clone → copy .env → docker-compose up →
  install → migrate → run). Keep this in the root README, don't fork it into
  a separate doc.

## Acceptance criteria

- A fresh clone + documented steps produces a running local Postgres and a
  passing `pnpm run migrate` (even against an empty schema) with no manual
  undocumented steps.
- `.env.example` covers every env var named in `docs/SPEC.md` for V1 (grep
  the spec for `_USD`, `_ENABLED`, `_GLOBAL` style names to check
  completeness).
- CI still passes.

# T13 — Bilingual variants

**Depends on**: T11.

## Goal

Ship the English-canonical/Telugu-derived content model end to end,
including QA and correction-driven invalidation — the trigger for **ADR-004
(bilingual content lifecycle)**.

## Scope

- `StoryVariant` rows per language (`en`, `te`) with `generated_at,
  model_version, qa_status` per §12's schema.
- English→Telugu generation through the AI gateway (T10), including glossary
  enforcement from §4.3: maintain glossary entries for names/places/
  organizations/domain terms; never blindly translate proper nouns with a
  known canonical Telugu spelling.
- Automated Telugu QA checks (§4.3): omitted numbers, dates, entities,
  currency, negation, and URLs between the English source and Telugu
  variant. Failing QA marks the variant unavailable and falls back to
  English (§4.2) rather than serving a broken translation.
- Correction propagation (§4.2, wired as a hook in T12): any approved
  English content correction invalidates the existing Telugu variant,
  queuing it for regeneration rather than silently serving stale text.
- Human review sample for political/legal/financial Telugu translations
  during the early-launch phase (§4.3) — implement as a sampling flag routing a
  percentage of these categories' Telugu variants into the review queue.
- Write ADR-004 covering: variant storage/versioning approach, fallback
  behavior when generation or QA fails, and the correction-invalidation
  mechanism.

## Acceptance criteria

- ADR-004 exists and is accepted.
- A story with no Telugu variant (or a failed-QA variant) correctly falls
  back to English in the API response, with the variant marked unavailable.
- Editing/correcting an English story invalidates its Telugu variant (test
  this transition explicitly).
- A glossary term used in a Telugu variant matches its canonical spelling
  in test fixtures, not a naive machine translation.
- Automated QA checks catch at least: a dropped number, a dropped date, and
  a dropped URL in test fixtures.

# T11 — Story generation

**Depends on**: T09, T10.

## Goal

Turn a clustered `Story` into a reviewable draft: classification, summary,
why-matters, and evidence-linked claims.

## Scope

- Run each `CLUSTERED` story through the AI gateway (T10): classify
  (categories/countries/entities/sensitivity/urgency), generate
  `summary_en` and `why_matters_en`, extract `claims[]` each linked to one
  or more `source_refs[]` (§7.4 — every important claim must point back to
  real evidence).
- Populate `StoryEntity`/`EntityAlias` and `StoryTopic` from the
  classification output.
- Apply the review-priority classification from §15: P0
  (breaking/legal/immigration/financial) → `REVIEW_REQUIRED`, always human;
  P1 (high importance/confidence) → `REVIEW_REQUIRED` if configured; P2
  (normal low-risk) → eligible for auto-publish after validation (T12/T06
  gate still applies); P3 (low-value/duplicate) → archived, not published.
- Advance the ingestion state machine to `ENRICHED` then `REVIEW` or
  `SCHEDULED` depending on priority tier.
- Apply the V1 publication rules table from §5.2 — immigration/legal/
  financial/breaking/obituary-accusation stories are never auto-published
  regardless of AI confidence.

## Acceptance criteria

- A story classified as immigration/legal/financial/breaking is always
  routed to `REVIEW_REQUIRED`, never auto-published — test this explicitly
  as a non-negotiable, not just a default.
- Every claim in a generated story has at least one `source_refs` entry;
  a story with an unsupported claim is held, not published (per §7.5).
- Low-confidence classification output lands in the review queue rather than
  proceeding.
- All AI calls here go through `packages/ai` from T10 — no direct provider
  calls.

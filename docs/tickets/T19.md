# T19 — Hardening

**Depends on**: T18.

## Goal

Close the release gates from §18 and §16 before launch — trigger
for **ADR-007 (production hosting/cost limits)**.

## Scope

- Security baseline from §16: TLS everywhere, managed secret store, MFA on
  admin sessions, RBAC audit, rate limiting on auth/search/admin, input
  validation/output encoding review, signed webhook verification (if any
  webhooks exist), dependency scanning + SAST wired into CI, encrypted
  backups configured and a **monthly restore test** actually run once.
- Privacy: confirm no-account browsing still works, coarse geography only
  (no GPS), no data sale, separate analytics consent, retention schedule
  documented, cross-system deletion job implemented and tested end-to-end
  (§5.5 — both in-app and public web deletion paths if accounts exist).
- Accessibility: run the full WCAG 2.2 AA audit across web and equivalent
  mobile checks (§3.4), fix criticals.
- Performance: verify reliability targets from §16 — API availability
  design, feed P95 < 800ms cached / < 1.5s uncached, story page < 1.5s, job
  success ≥95% first/retry, zero known duplicate publishes, load test feed
  and search.
- Golden AI regression set (§18): ≥300 representative stories across
  categories/entities/multilingual cases with expected labels/facts/
  entities/translation invariants; wire it to run on every prompt/model
  change, not just once.
- App-store readiness (§25): Apple/Google privacy disclosures match actual
  runtime data collection; support/privacy/deletion URLs live and stable;
  store metadata/screenshots accurate.
- Simulate and verify each failure mode: broken source (T08's circuit
  breaker), AI failure (T10/T11's hold behavior), cost-guardrail breach
  (T10/T19 budget), and correction/retraction (T12/T13).
- Write ADR-007: hosting platform choice(s) and concrete cost limits/alert
  thresholds for production.

## Acceptance criteria

- Every release gate listed in §18 passes: no P0/P1 security defects, all
  migrations tested, no rights-disabled source can publish, no sensitive
  story bypasses review, English correction invalidates Telugu variant,
  account deletion works E2E, notification dedupe verified, rollback
  verified, backup restore verified, AI eval within agreed regression
  threshold.
- ADR-007 exists and is accepted.
- Load test results meet the P95 targets in §16 or a documented follow-up
  plan exists if not yet met.
- Accessibility audit has no critical violations remaining.

## Focused recovery follow-up (2026-10-01)

Under the existing R3/single-VPS recovery tooling, make restore drills safe to
run concurrently: isolate database and plaintext-file names, delete only a
database this invocation successfully created, clean partial dumps after
failure, and report success only after validation and cleanup succeed. Preserve
the existing schema/count comparison and RTO/RPO data points; no migration or
recovery-policy changes. A requested failed drill must also make the surrounding
`ops-evidence.sh --drill` report exit nonzero while finishing its observations.

Acceptance: scoped shell syntax checks and subprocess regression tests covering
concurrency, failed CREATE ownership, partial decryption, restore failure,
schema/data mismatch, cleanup failure and wrapper failure propagation. Run those
tests in CI. Update the recovery runbooks and progress with local evidence and
limitations. These tests do not close production backup/restore/alert gates;
those still need a real VPS drill, RTO/RPO, offsite copy and confirmed receipt.

# X2 — Incremental X fetch

**Depends on**: X1, T07. **Insert after**: T07, before X3.

## Goal

Implement the X adapter's fetch side, following the same adapter contract
as every other source, with strict incremental/rate-limit/cost discipline.

## Scope

- Use the official X API user-posts timeline endpoint
  `GET /2/users/{id}/tweets` (pagination, exclusion filters,
  `since_id`/time filtering) — current docs at
  `docs.x.com/x-api/posts/timelines`. **Never** scrape the public X website;
  if API access is unavailable, set the source to `DISABLED` or keep it
  `LINK_ONLY` until access is restored (§6.3.1).
- Fetch only new posts using persisted `since_id`; never re-fetch full
  timelines (§19 cost control).
- Bounded retries with backoff on errors; explicit handling for HTTP 429
  (back off, don't hammer).
- Polling cadence: high-priority approved accounts may use 1-5 minutes where
  permitted; treat this as a target, not a guarantee — respect the source's
  actual rate limits and terms.
- Cost telemetry: track `x_api_posts_read`, `x_api_cost_estimate`,
  `x_api_budget_remaining`, and rate-limit error counts (§19) — feed the
  same budget-guard mechanism pattern as T10's AI budget guard.
- Fits into the T08 job-queue pattern as a distinct job type
  (`x_official_account_fetch` per §14) — claim due accounts, never poll
  disabled or budget-blocked accounts.

## Acceptance criteria

- Fetch calls only request posts newer than the stored `since_id`; a test
  verifies no duplicate/older posts are re-requested.
- A 429 response triggers backoff, not an immediate retry storm.
- No code path in this adapter falls back to scraping x.com HTML.
- Cost telemetry fields are populated after each fetch run and are visible
  wherever T10's AI cost telemetry is surfaced (or an equivalent admin
  view — X4 builds the dedicated view, this ticket just needs the data to
  exist).

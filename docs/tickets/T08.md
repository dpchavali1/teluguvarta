# T08 — Ingestion worker

**Depends on**: T07.

## Goal

Turn the manual adapter calls from T07 into a scheduled, reliable pipeline
stage using the Postgres job queue — this is the **trigger for ADR-003
(database job queue strategy)**.

## Scope

- Implement the `jobs` table pattern from §14: workers claim jobs via
  transactional row locking on `status, run_after, attempts, lock_expiry,
  dedupe_key`. Write ADR-003 covering: exact claiming SQL pattern (e.g.
  `SELECT ... FOR UPDATE SKIP LOCKED`), worker deployment shape (managed cron
  trigger vs. one lightweight always-on worker — pick one and justify it
  against cost/ops-complexity goals in §19), and retry/backoff parameters.
- `source_fetch` job: runs each active, non-`DISABLED` source's adapter on
  its `refresh_minutes` cadence, dedupes by `SourceItem(source_id,
  external_id)`, updates `Source.fail_count/last_success_at/last_error_at`.
- Failure handling per §6.5: exponential backoff for transient errors,
  circuit breaker after repeated failures, health state visible in admin
  (surface via the `/v1/admin/sources` fields from T06), bounded retries
  with a terminal failed-job record — never an infinite retry loop.
- Idempotency: `SourceItem` dedupe key is stable per source item; re-running
  a job for the same item must not create duplicates.
- Ingestion state machine from §6.4: `DISCOVERED -> RIGHTS_BLOCKED |
  NORMALIZED -> DEDUPED -> CLUSTERED -> ENRICHED -> REVIEW | SCHEDULED ->
  PUBLISHED -> UPDATED | RETRACTED`. This ticket only needs to get items to
  `NORMALIZED`/`RIGHTS_BLOCKED` — later tickets advance the rest.

## Acceptance criteria

- ADR-003 exists and is accepted.
- Two workers racing to claim the same job never both process it (test with
  concurrent claim attempts).
- A source with `rights_status = DISABLED` never produces a published item
  path — items from it land in `RIGHTS_BLOCKED`, not further.
- Repeated source failures trip the circuit breaker and are visible via the
  admin source health fields; retries are bounded and observable.
- Re-running `source_fetch` against the same fixture data produces zero
  duplicate `SourceItem` rows.

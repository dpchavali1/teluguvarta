# User-experience review — 2026-09-12

The highest-value next step is to make the core reading journeys dependable.
The product already has recognizable editorial styling, public browsing,
visible source links, bilingual story variants, and reusable story cards.
Several interactions still fail to deliver the behavior their labels promise.

This is a review and proposed implementation order, not an approved expansion
of the specification or a claim that these findings have been fixed.

## Scope and evidence

- Read BUILD_ORDER, current progress, NON_NEGOTIABLES, T14, and relevant ADRs.
- Inspected web/mobile reading, onboarding, search, saving, language state,
  API ranking/search/serialization, analytics, and the admin review queue.
- Viewed the running local web home and story detail at desktop size and
  390 × 844. Local data contains a seeded demonstration story, not a
  representative production corpus. Visual findings include the current
  typography changes present in the workspace.
- Queried the local public API for the seeded story and a Telugu search.
- Reproduced repeated mobile home requests with a bounded temporary Jest
  probe using the real HomeScreen, API normalization, and StoryCacheProvider;
  navigation and the card renderer were mocked. Removed the probe afterward.
- Reference revision at final source check: `4afc283`. The working tree
  changed externally during the review; application edits were not made by
  this review. Recheck locations against the implementation baseline.
- No native device, screen-reader, production-load, live-AI-quality, or full
  security audit was performed. This is not a WCAG conformance certification.

## Findings, in priority order

### 1. P1 — Mobile cache updates repeatedly refetch the same screen

**Evidence:** `apps/mobile/src/lib/StoryCacheContext.tsx:41` increments a
version whenever an incoming story has a new object identity. That version
changes the context value at line 66. `HomeScreen.tsx:72` depends on the whole
context object, so its fetch callback changes and its effect runs again.
The API normalizer creates fresh story objects even for unchanged responses.
`TopicScreen.tsx:39` and `StoryDetailScreen.tsx:37` share the dependency pattern.

**Verified:** One HomeScreen mount issued five home requests without any
interaction. The probe stopped returning responses after the fourth to keep
the reproduction bounded. This supports repeated fetching; it is not a
measurement of device battery or production traffic.

**Impact:** Repeated requests and analytics events; possible loading flicker,
extra bandwidth, and work on inactive screens.

**Fix:** Depend on stable cache operations such as `put`, separate state
subscriptions from fetch triggers, and cancel/ignore obsolete requests.
Keep cache updates reactive for saved indicators.

**Acceptance:** An idle mounted screen stops fetching after initial load;
saving or switching language does not fetch the feed; explicit refresh
fetches once; Home, Topic, and Detail are covered with fresh response objects.
React documents the underlying dependency cycle in its
[useEffect guidance](https://react.dev/reference/react/useEffect#my-effect-keeps-re-running-in-an-infinite-cycle).

### 2. P1 — Saved stories are not reliably recoverable

**Evidence:** Web `apps/web/src/app/saved/page.tsx:30` fetches only the latest
100 stories and filters saved IDs against them. Mobile
`apps/mobile/src/screens/SavedScreen.tsx:21` resolves IDs only from the
in-memory story cache, which starts empty on process restart. Missing mobile
entries are dropped, and the empty message says nothing was saved.

Web's saved-page request also has no status check or catch; an offline or
bad response can leave it displaying Loading indefinitely. In
`apps/web/src/lib/saved.ts`, a failed storage write still returns success,
so the button can claim Saved when nothing persisted.

**Fix:** Define a durable local saved reference including the canonical slug
and resolve it through the existing story endpoint. Specify migration for
old ID-only saves; if a bulk endpoint is chosen, document the contract change.
Show unavailable, loading, and retry states explicitly. Revalidate current
correction/retraction status; do not treat a cached snapshot as current.

**Acceptance:** Save → terminate app → reopen Saved works without revisiting
the feed; a story older than 100 newer entries still opens; offline, storage
denial, correction, and retraction cases have truthful outcomes.

### 3. P1 — Web onboarding promises personalization the main feed never uses

**Evidence:** `apps/web/src/app/page.tsx:13` calls parameterless `getHome()`;
`apps/web/src/lib/api.ts:81` calls `/v1/home` without profile parameters.
The browser profile is used for Student Briefing, but not the main feed.
`OnboardingCta.tsx` nevertheless says “Feed personalized for …”.

There are further disconnected pieces: both story cards render only
`variant.why_matters`, ignoring `story.personalization.why_matters`. Web asks
for country as free text with “United States” as its example, while
`apps/api/app/content/ranking.py:67` matches the input directly against
country codes such as `US`. Merely forwarding the existing form is insufficient.

**Fix:** Complete the profile-to-feed path with normalized country values,
preserve an immediately browsable anonymous feed, and use the personalized
explanation only under a defined language/QA policy. Do not insert an English
personalized sentence into a Telugu-labelled passage without handling language.

**Acceptance:** With a representative seeded corpus, changed residence/topics
produce the expected ranking and an accurate explanation. Skip still works.
Student and professional profiles use the same backend. Claims in the UI
match the ranking actually used.

### 4. P1 — Telugu words cannot find Telugu stories

**Evidence:** `apps/api/app/routers/public.py:253` restricts search to English
variants. The local published story contains “వీసా” in its QA-passed Telugu
headline; `GET /v1/search?q=వీసా` returned `items: []`.

**Fix:** Search displayable English and QA-approved Telugu variants in
Postgres, deduplicate story IDs, and retain publication/translation gates.
Do not introduce another search service. Treat transliteration and synonym
tuning as later measured improvements.

**Acceptance:** Exact words from either displayed language find the story;
failed or invalidated Telugu variants do not influence public results;
matching both variants does not duplicate the story.

### 5. P1 — Native story detail cannot scroll long content

**Evidence:** `apps/mobile/src/screens/StoryDetailScreen.tsx:65` places the
entire card in a plain `View`. There is no vertical scrolling container.
Summary, why-it-matters, attribution, and actions can exceed a phone's height,
especially with Telugu text or larger accessibility text settings.

**Fix:** Use a scrollable reading surface with appropriate safe-area spacing.
Keep the full content and source/action controls reachable.

**Acceptance:** On small iOS/Android screens and enlarged system text, users
can scroll to and activate the source, save, and share controls.

### 6. P1 — Issue reporting confirms receipt before receipt is known

**Evidence:** `apps/web/src/components/StoryCard.tsx:86` immediately clears
the input and claims the issue was logged. `apps/web/src/lib/analytics.ts`
sends a best-effort request and suppresses failures. `/v1/events` writes
analytics logs; this path does not create an editorial review task.

**Fix:** Only confirm a report after acknowledged receipt, preserve the draft
on failure, and provide retry. If reports must enter an editorial inbox,
record the ownership, retention, and workflow decision before implementing it.
Analytics emission alone is insufficient evidence of a review workflow.

**Acceptance:** An offline submission retains the description and shows a
retry state. A confirmed submission has an identified, retrievable destination.

### 7. P2 — Language state is inconsistent and fallback is mislabeled

**Evidence:** Web StoryCard selects the English fallback at line 47 but sets
`lang={language}` at lines 117–123. A Telugu preference with no Telugu variant
therefore labels English text as Telugu. The header LanguageToggle reads the
preference only at mount; card controls broadcast a change which other cards
receive, but the header does not subscribe to it.

**Fix:** Render language attributes from the actual variant, explain English
fallback briefly, synchronize all controls from one language state, and
distinguish story-language preference from full interface localization.

**Acceptance:** Header and cards agree after any language change; absent
translations identify English correctly. This follows
[W3C language-of-parts guidance](https://www.w3.org/WAI/WCAG22/Understanding/language-of-parts).

### 8. P2 — Mobile search can display results for an obsolete query

**Evidence:** `apps/mobile/src/screens/SearchScreen.tsx:20` debounces input,
but every completed request writes results regardless of the current query.
Clearing the field also does not invalidate an already running request.

**Fix:** Abort obsolete requests where possible and use a request generation
guard so old success, error, and finally handlers cannot replace newer state.

**Acceptance:** Resolve request A after request B; B remains visible. Clear
while searching; the old results do not return. Keyboard Search submits once.

### 9. P2 — Home delays the first useful story and offers weak discovery

**Observed:** At desktop size the first headline was below the initial
viewport. At 390 × 844, the three-row header, large brand hero, CTA, and topic
rail consumed most of the screen; the first headline began near the bottom.
The alphabetic topic rail contained 26 topics, including many empty categories
in this local seed. See `apps/web/src/app/page.tsx` and `globals.css:546`.

**Recommended design direction:** Keep the editorial identity, reduce the
home hero, and foreground the briefing and first story. Make the existing
Topics page an obvious destination from a shorter, readable topic rail.
Show publication/update time on cards, use readable topic names instead of
raw slugs, and make active navigation clear. Keep source attribution prominent.

Country pages discard `next_cursor`; topic pages show a fixed maximum of
50 stories. Provide an explicit route to older results using existing paging
where available, with a specified contract extension if needed.

**Acceptance:** A useful headline and context fit in the first phone viewport;
navigation remains usable with enlarged text; older stories remain reachable.
Verify EN/Telugu, keyboard focus, light/dark themes, and small screens with
realistic content density. No source images or share-card images are needed.

### 10. P2 — Feed latency can grow with AI and archive size

**Evidence:** `apps/api/app/routers/public.py:185` invokes segment-specific
generation sequentially in the feed response path. On a cache miss,
`apps/api/app/content/why_matters.py:67` makes a synchronous gateway call.
The helper's claim that it never blocks the response is inaccurate.

Separately, `_published_story_ids()` reads all matching IDs before callers
slice to 10/50/a page. Story serialization performs additional queries per
story and source. These are code-level scaling risks, not measured production
latency findings.

**Fix:** Serve validated cached/generic explanations promptly and prepare
missing segment explanations through the existing bounded Postgres jobs,
subject to the existing review policy. Bound selection in SQL, batch related
rows, and measure warm/cold feed latency before and after.

**Acceptance:** Feed availability does not depend on a live AI provider;
archive growth does not require reading every story ID for the first page;
query counts and response time are measured on representative data.

## Follow-on improvements and verification

- The admin queue lists reason/status/date but no headline or source context
  (`apps/admin/src/app/review/page.tsx`). Add enough context for an editor to
  triage without repeatedly opening indistinguishable rows. Preserve the
  human-review gates and require an actual browser pass before claiming the
  admin workflow was validated.
- Resolve proposed ADR-009 before implementing a shared token architecture.
  Use it to address theme/type consistency across surfaces, after the journey
  defects above. A new framework or major visual rewrite is not a prerequisite.
- Existing web axe checks run in jsdom without layout or real hydration;
  `tests/e2e/README.md` is a placeholder and CI does not run browser journeys.
  Add browser/device regression coverage for the acceptance checks above,
  including slow/out-of-order requests and app restart. Lint and typecheck
  alone cannot establish good UX or accessibility.
- The progress tracker still records 270 AI-generated eval items without human
  review and no live-provider golden-set run. Validate Telugu readability and
  evidence quality with native speakers and editors before treating the count
  of 300 examples as a quality guarantee.
- The local seed has an immigration headline with `sensitivity: NONE` and a
  category-page source link. Treat it as demonstration content only when
  assessing trust badges or content quality, not production editorial evidence.

## Suggested delivery order

1. **Reliability:** repeated requests, mobile scrolling, obsolete search results,
   and honest save/report failures. Add focused regression coverage.
2. **Complete the promise:** durable saved retrieval, real profile-driven home,
   Telugu search and accurate language fallback. Resolve any contract/workflow
   decisions explicitly before implementing beyond existing scope.
3. **Reading and speed:** compact home, clearer labels/freshness/navigation,
   accessible controls, bounded database reads, cached feed explanations.
4. **Validate:** test realistic journeys with Telugu readers, students,
   professionals, and parents, including people using larger text. Measure
   time to a useful story, save/reopen success, search success, source-link
   usage, and repeat visits. This is a recommended usability study, not a
   reinstatement of the waived T20 launch gate.
